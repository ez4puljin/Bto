# ADR-0186: The centre runs on the store's Ubuntu PC, beside the store edge, until the external server

| | |
|---|---|
| Status | Accepted |
| Date | 2026-11-11 |
| Deciders | Owner (2026-11-11: «Дэлгүүрийн Ubuntu дээр төвийг хамт ажиллуул»), Claude (a worker session) |
| Amends | ADR-0026 #1 and #3 (a production footprint exists before the go-live phase: the store PC carries the centre for the supermarket's pilot; the external server stays the go-live target), ADR-0063 (its last follow-up: where the centre runs on the cut-over day), ADR-0067 #10 and ADR-0136 (the edge on the centre's own PC; how a dev edge becomes the production edge) |

## Context

The supermarket is to pilot one real till on Bto, and the wholesale e-Barimt (ADR-0185) needs a centre that reaches the store's PosAPI on the store's LAN. ADR-0026 planned no deployment before the go-live phase, and no external server, domain or managed database exists. ADR-0063 left the question open (STATUS pending decision #30): the droplet opened early, or the store PC carrying the centre and the edge until go-live. The owner chose the store PC.

The machine, read on 2026-11-11 (read only): `bto-edge@192.168.1.152` on the store's LAN, Ubuntu 26.04, an i3-10100 (8 threads), 7.1 GB of memory with swap in use, **one** 233 GB disk with 169 GB free, Docker 29 with Compose 2.40, the firewall (`ufw`) on, the clock on Asia/Ulaanbaatar. It runs the dev edge stack of `deploy/edge` (kiosk on port 7400, e-Barimt provider `fake`), linked to the dev centre on the owner's PC, with 13 rejected test documents in its outbox. Port 80 is free. The store's PosAPI is another PC (192.168.1.254:7080).

The dev database `bto_main` on the owner's PC holds the real master data (12 867 products, 1 404 customers, 380 suppliers, 48 staff, the chart of accounts as the accountant arranged it) mixed with test documents.

## Decision

1. **A third stack, `deploy/store`** (`docker-compose.store.yml`, project `bto-store`), on the store PC beside the edge stack: `postgres` (PostgreSQL 18, UTF-8 and ICU `und`, data on the volume `bto-store_pg`), `api`, `worker` (the `bto-api` image, built on the box from the checkout as `bto-api:store-local`; no registry) and `web` (the `bto-web` image as `bto-web:store-local` with `Caddyfile.store`: the admin's pages and `/api`, `/health` passed to the api). Uploaded files live on the volume `bto-store_storage`, mounted by api and worker. Two one-off services, `provision` and `migrate`, run `dist/db/provision.js` and `dist/db/migrate.js`; `provision` is the only container that sees the PostgreSQL superuser's password. Every variable a container reads is named in the compose file; nothing is passed wholesale from the `.env` file.
2. **Addresses.** Staff open `http://<the box's LAN address>` (port 80, `STORE_HTTP_PORT`); the tills keep `http://<the box>:7400` of the edge stack. PostgreSQL is published on the box's loopback only (`127.0.0.1:15433`, `STORE_PG_PORT`) for the seed over an SSH tunnel and `psql` on the box.
3. **LAN-only HTTP until the external server.** No port is forwarded from the internet, no domain, no certificate, no Tailscale. It means: the system is used only inside the store's network (the office and the wholesale warehouse share the building and the LAN); the staff app works on the store's Wi-Fi only, with a build whose server is the box (`BTO_SERVER=http://<the box>`); the customer app «Bto300» stays on the test server; `COOKIE_SECURE=false`; the browser's camera scanner does not work over plain HTTP (USB scanners and the apps do); the AI assistant and the taxpayer lookup still need the box's outgoing internet. The external server of ADR-0026 #3 brings HTTPS and outside access; moving there is a dump and restore of this database, not a second seed.
4. **Secrets are made on the box.** `deploy/store/setup.sh` writes `deploy/store/.env` (mode 600, gitignored) with fresh random values for the PostgreSQL superuser and the three roles, `JWT_SECRET`, `AUTH_PEPPER`, `POS_PIN_PEPPER` and `AI_KEY_SECRET`, and never prints one. It is safe to run again: it adds only variables the file lacks, rebuilds, provisions, migrates and starts. Nothing of the dev environment's secrets moves to the box. Consequences, by design: every session starts anew (staff sign in again, with the passwords they have), every cashier's PIN is set again (the PIN hashes are keyed by `POS_PIN_PEPPER`), and the AI key is typed again on «Тохиргоо → AI» (sealed with `AI_KEY_SECRET`).
5. **Sizing for 7 GB shared with the edge.** PostgreSQL: `shared_buffers` 512 MB, `effective_cache_size` 2 GB, `work_mem` 8 MB, `max_connections` 40, memory limit 1.5 GB. Pool budget: api 6 + 1 live stock listener, worker 2, pg-boss 2 per process, the AI reader 2 → 15 of 40, the rest for the migrator, the nightly dump, the seed and `psql`. Memory limits: api 1 GB, worker 768 MB, web 128 MB.
6. **A clean start database: master data only.** `pnpm store:seed` (`apps/api/src/db/store-seed`, `tools/store-seed/README.md`) copies master data from a source database into a target that was migrated and never started. It is a dry run unless `--apply` is given.
   - Every table is named once in `manifest.ts` as **copied**, **left empty** or **not decided** (left empty too). A table a later migration adds and nobody listed is «not decided».
   - The target must be on the same migrations as the source, and empty: every table without rows, except the reference rows the migrations themselves write. A database somebody started or worked in is refused, and nothing is written into it. The setup script therefore stops before the first start of an empty database and says so.
   - The source is read in one read-only snapshot. The target is written in one transaction as the role that owns the tables (`migrator`), by plain `INSERT`s in foreign-key order: no trigger is disabled, no constraint relaxed, nothing is deleted from a table that holds documents. A row may point only at copied rows, or the plan is refused. Afterwards every copied table is counted against the plan and the identity sequences are set past the highest copied id; any difference rolls everything back.
   - Reference rows the migrations wrote in the target are made the source's by primary key (a changed account name, a row that has another id in the source). `fin.posting_rules` is append-only: its rows are matched by what they say and the source's later rules are appended with new ids; the rule in force per key and date must then say the same on both sides.
   - What never travels: tokens and codes (`pos_edge_nodes` without its token, link code and last-seen facts; `pos_tills` without pairing codes), the cashiers' PINs, sessions, one-time codes, the sealed AI key.
   - Files: the rows of the files of copied records (product pictures, staff photos); the tool writes the list of those files so they are carried into the storage volume, with the published APKs.
   - The 2026-11-11 run against a copy of the dev database: 122 810 rows into 98 tables, every copied table identical to its source by checksum except the four that differ on purpose (`files`, `pos_edge_nodes`, `pos_tills`, `fin.posting_rules`); the stock and finance reconciles of the result report no drift; the api starts on it.
7. **What moves** (the tool's dry run prints the same list with the row counts):
   - **Copied (98 tables).** Identity and organisation: `users` (with their password hashes), `roles`, `permissions`, `role_permissions`, `role_permission_overrides`, `user_roles`, `user_company_roles`, `user_scopes`, `branches`, `settings`, `company_contacts`, `files` (of copied records only). Warehouses and catalog: `warehouses`, `bins`, `uoms`, `categories`, `products`, `product_units`, `product_barcodes`, `product_images`, `product_locations`, `product_suppliers`, `segments`, `segment_products`. Partners: `customers`, `customer_categories`, `customer_addresses`, `customer_contacts`, `suppliers`, `supplier_categories`, `supplier_contacts`, `supplier_orderers`, `trucks`. Pricing: `price_profiles`, `price_profile_versions`, `product_prices`, `discount_programs`, `discount_program_links`, `discount_steps`. Stock setup: `issue_expense_types`. Sales setup: `sales_boards`, `sales_pipelines`, `sales_pipeline_roles`, `sales_stages`, `sales_stage_roles`, `sales_channel_defaults`, `sales_settings`, `sales_document_templates`, `sales_document_template_versions`, `rep_visit_plans`. Finance setup: `finance_settings`, `statement_row_links`, `bank_statement_settings`. The tills: `pos_settings`, `pos_edge_nodes`, `pos_tills`, `pos_till_users`, `pos_till_categories`, `pos_payment_types`, `pos_quick_groups`, `pos_quick_buttons`, `pos_receipt_templates`, `pos_receipt_template_versions`, `pos_loyalty_tiers`. HR: `hr_divisions`, `hr_employees`, `hr_employee_children`, `hr_employee_sites`, `hr_work_sites`, `hr_schedules`, `hr_settings`, `hr_event_types`, `hr_request_types`. The apps: `app_settings`, `app_stock_warehouses`, `staff_app_assortments`, `staff_app_assortment_segments`, `staff_app_assortment_users`. «И-баримт шалгах» setup: `ebarimt_check_accounts`, `ebarimt_check_supplier_profiles`, `ebarimt_check_assignments`. The Finance Core's organisation and chart: `fin.tenants`, `fin.companies`, `fin.company_tax_registrations`, `fin.branches`, `fin.branch_refs`, `fin.source_systems`, `fin.source_grants`, `fin.account_groups`, `fin.accounts`, `fin.money_accounts`, `fin.document_types`, `fin.number_series` (the patterns), `fin.posting_keys`, `fin.posting_rules`, `fin.parties`, `fin.party_companies`, `fin.party_refs`.
   - **Left empty (119 tables).** Stock: `stock_ledger`, `bin_stock`, `warehouse_stock`, `lots`, `stock_reservations`, the snapshots, `stock_valuation_adjustments`, adjustments, bin moves, transfers and transfer requests, goods receipts and issues with their lines, confirmations and discounts, stocktakes and stock counts. Procurement: purchase orders with their lines, suppliers, loads and invoice checks. Sales: orders with their lines, parts, picks, loads, changes, stage moves and status events, `rep_visits`, `rep_collections`. Money: `invoices`, `credit_notes`, bank statements, the wholesale e-Barimt receipts (`ebarimt_receipts`, ADR-0185), and of the Finance Core `fin.documents`, `fin.journal_entries`, `fin.journal_lines`, `fin.open_items`, `fin.allocations`, `fin.party_balances`, `fin.number_counters`, `fin.intake_requests`, `fin.intake_attempts`, `fin.period_events`. 8. **Stock and books are not invented.** Stock starts at zero: before the pilot day the supermarket floor is counted with «Тооллого» (ADR-0176, ADR-0177, ADR-0181) or loaded with the opening-stock import; the owner's step. The books start empty and their opening stays the accountant's cut-over step (ADR-0102). Pilot sales post into Bto's books from the first sale, while Erkhet stays the company's official books until the cut-over (ADR-0077). **TODO-VERIFY (architecture §13.2 T41, the accountant):** how the pilot period is treated at the cut-over, and whether the pilot till's sales are also entered into Erkhet as today. Nothing is decided here.
9. **Backups that leave the machine.** `deploy/store/backup.sh`, run nightly at 02:30 as root by a systemd timer (`install-backup-timer.sh`): a `pg_dump` archive of the centre and of the edge database with every table's row count, the roles, the two `.env` files, checksums, and a mirror of the uploaded files, in `/var/backups/bto` (`daily/<date>`, kept 14 days; `storage/`). When a USB disk is mounted at `/mnt/bto-backup` the night's folder and the mirror are copied there and kept 90 days. The second copy is pulled from the owner's PC over SSH (`tools/store-backup/pull.ps1`), which also shows the last run's result (`last-run.txt`) and checks every file against its checksum. `restore-drill.sh` restores a night into a scratch database `restore_drill` beside the live one, compares every table's count with the counts written at backup time and drops it; fewer rows than counted fail the drill. `housekeeping.sh` prunes Docker's build cache and unused images, never a volume; the backup does the same for the cache every Sunday.
10. **The dev edge becomes the production edge with a fresh database, in the same PostgreSQL.** With the tills' shifts closed and nothing pending, the edge and the kiosk are stopped, the edge database is renamed inside its own cluster (`tugeel_edge` → `tugeel_edge_dev_<date>`) and an empty `tugeel_edge` is created; the edge migrates it at its next start and the kiosk shows «Төв системтэй холбох». It is linked with a one-time code of the new centre (ADR-0136) at the address `http://host.docker.internal` (the centre on the same PC, through port 80); the tills open by address (ADR-0138). Nothing is deleted and no volume is removed: the dev sales and the 13 rejected test documents stay in the renamed database, which the edge never opens again. `EBARIMT_PROVIDER` stays `fake` until the owner switches it for the pilot day; from that moment every receipt is a real tax receipt.
11. **Updates and roll-back.** Update: `git pull`, `bash deploy/store/setup.sh` (the api applies the migrations as it starts), then the edge's `setup.sh`: the centre first. Roll-back of code: check out the previous commit and run the script again, only to a commit whose code works with the migrated schema (migrations are forward-only). Roll-back of data: the last night's dump. When the box dies: a new PC, the same two stacks, the last dump from the USB disk or the owner's PC (`docs/runbooks/store-install.md`).
12. **CI.** The `deploy-config` job validates `deploy/store/docker-compose.store.yml` with `.env.example`, the edge compose file together with `deploy/store/docker-compose.edge-link.yml`, and `Caddyfile.store`; the seed has an integration suite (`store-seed.int-spec.ts`).

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| Open the external server now | No hosting, domain or managed database exists; the owner wants the pilot first. The store's PosAPI is on the internal line, so the centre would still need a way in to it (ADR-0185 solves that through the edge, on either side). |
| Keep the centre on the owner's PC for the pilot | A development machine that restarts, sleeps and migrates at will cannot carry real sales and real tax receipts. |
| Copy the whole dev database and delete the test documents | Deleting from the ledger, the journal and the audit log means disabling the append-only guards; the result would be a database whose history was edited. An empty, migrated database with copied master data never held a document. |
| `pg_dump --data-only` of chosen tables | Cannot overwrite tokens and codes, cannot take only the files of copied records, cannot reconcile the rows the migrations seed (same key, another id), and says nothing about a table nobody classified. |
| Carry the dev secrets (PIN key, AI key seal) so nothing is set again | Secrets that lived in a development `.env` are not production secrets; setting PINs and the AI key again is a few minutes. |
| A fresh Docker volume for the production edge, or `down -v` | Removing or replacing the volume risks the old data and changes the project the scripts and the backup know; a renamed database in the same cluster keeps everything and changes nothing else. |
| Re-link the dev edge to the new centre | Its outbox, sale numbers, device bindings and rejected documents would come along; ADR-0136 already rules that a linked edge does not move to another centre. |
| A shared Docker network between the two stacks as the only path | The edge's own scripts would have to know the store stack. It stays the fallback (`docker-compose.edge-link.yml`, address `http://api:3000`) if the host route fails on the box. |
| HTTPS with a private certificate on the LAN | Every phone, till and PC would need the certificate installed; the external server brings real HTTPS. |
| Tailscale or a forwarded port for outside access | The owner asked for neither; an exposed HTTP port would publish sign-ins in the clear. |

## Consequences

**Positive.** One real till can sell on Bto without waiting for the external server; the wholesale e-Barimt reaches the store's PosAPI on the same LAN; production starts from a database that never held a test document; the move, the backup and the restore are scripts that were rehearsed on real data; the deploy files stay validated by CI.

**Negative.** One PC with one disk carries the centre, the edge and both databases: until the external server the nightly copy off the machine is the only protection, and a dead box stops the office's screens (the tills keep selling through the edge only while the box itself runs). 7 GB of memory is tight for a build during opening hours: updates are done outside them. Plain HTTP on the LAN shows sign-ins to anyone who can listen on that network. Test sign-ins of the dev database travel with the staff: they are disabled on the new system before anyone else signs in. The books of the pilot period live beside Erkhet's until the accountant says how they meet.
