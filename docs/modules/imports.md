# Module `imports` — contract

Status: **built** in delivery 1 (week 4), session of 2026-10-11; accepted locally together with the rest of delivery 1. Code: `apps/api/src/modules/imports/`, shared rules in `packages/shared/src/imports`, screens in `apps/web/src/features/imports/`. Decisions: ADR-0015 (pipeline), ADR-0081 (the issues sheet), ADR-0036 (as built: all or nothing, parsed by the worker), ADR-0013 (pg-boss), ADR-0030 (local file storage), ADR-0027 (access control), ADR-0040 (housekeeping), ADR-0044 (no brands, new products wait for their prices, the table order of product writers), ADR-0054 (the price sheet, 2026-10-15), architecture §4 (imports row).

imports depends on `identity` (files, audit, warehouses, actors), `catalog`, `partners`, `inventory` and `pricing` (ADR-0054), always through their `index.ts` and their `*InTx` / bulk methods inside its own transaction; it never writes another module's tables. Nothing imports `imports` in-process.

## 1. Owner's answers behind the design (interview of 2026-10-11)

- **A file with any error is refused entirely.** The owner fixes the sheet in Excel and uploads it again; nothing is half-imported.
- **References are created by hand first.** A category, supplier, warehouse or shelf missing from the system is an error, so typos never create new master data. (Brands were removed on 2026-10-13, ADR-0044.)
- **New products wait for their prices (2026-10-13, ADR-0044).** A product the import creates is «Үнэ хүлээгдэж буй» until a price clerk completes it, also in bulk from `/catalog/pending`. Codes from the sheet are kept as they are: the category code ranges do not apply to imports.
- **Opening stock** comes from today's spreadsheets per warehouse, without shelves and without costs (costs stay 0 until a later decision).
- **Sheets.** The product sheet has one box-quantity column and several barcodes in one cell; the customer sheet has no company/individual column. The owner fills the system's templates (columns found by their headers), saves `.xlsx`, and only admins import.
- **Public repository.** The owner's real files never enter the repository; tests use synthetic data and logs carry counts only.

| Method and path | Notes |

PRICES is filled (ADR-0054 #2): every active product by code with name, base unit, packs («хайрцаг 24») and the terms in force today, the day column as text, and a sheet «Тохиргоо» with the live profiles and their values today |

## 5. Pipeline (ADR-0036)

- **Jobs.** Queues `imports.validate` (retry 2, expire 900 s), `imports.commit`, `imports.revert` (retry 1, expire 3,600 s): policy `exclusive`, `singletonKey` = the import id, heartbeat 60 s, kept 7 days. The handlers in `jobs/*.job.ts` only call `ImportPipelineService`.
- **Reading.** The worker opens the file through `StorageService.openPrivate`, loads the workbook with ExcelJS 4.4 (whole workbook; the streaming reader loses shared strings and hyperlink targets), takes the first sheet, finds the header row in the first 10 rows by the labels and aliases of `mn.json` (`matchHeaders`), and stores at most 20,000 rows (50,000 for PRICES, ADR-0054) × 60 columns, 1,000 characters per cell. Cells: numbers become text without float noise, formulas give their stored result (none → `FORMULA_WITHOUT_RESULT`), dates in a code or quantity column are refused, hyperlinks give their address (Google Maps links → GPS), a numeric code whose check digit shows a lost leading zero is restored with `NUMERIC_CODE`. File-level problems (`EMPTY`, no header, unknown or duplicate columns, too many rows, unreadable) end in FAILED with `summary.fileIssues`.
- **Checking.** Each importer normalises its rows with the shared rules (`@tugeel/shared/text`, `gtin`, `units`, `phone`, `taxpayer`, `geo`, `inventory`), looks everything up in bulk, marks duplicates inside the file (`DUPLICATE_IN_FILE` names the first row) and against the database (`TAKEN`), and plans CREATE / UPDATE / UNCHANGED with the changed fields. Rows are stored in chunks of 1,000; progress every 250 rows.
- **Commit.** One transaction: `IMPORT_LOCK`, re-validation against the current database (a different outcome rolls back, stores the new preview with `summary.refreshed` and leaves the job VALIDATED or INVALID), then every row through the owners' bulk services under table locks (no per-product advisory locks, so 10,000 products fit one transaction). Progress goes through a separate pool connection; the job row changes in the transaction only at the end. A failure rolls everything back and returns the job to VALIDATED with `last_error`.
- **Revert.** One transaction under `IMPORT_LOCK`, LIFO across all kinds (only the newest committed import). A failure leaves the job COMMITTED with `last_error`.
- **Housekeeping** (ADR-0040): `imports.housekeeping` runs every night at 04:00 Ulaanbaatar time. It deletes the rows of INVALID, FAILED and REVERTED imports 90 days after their last change (one import per transaction, `summary.rowsPruned`); committed imports keep theirs for the revert. A year after the upload (ADR-0014) the sheet of a VALIDATED, INVALID, FAILED, COMMITTED or REVERTED import is marked DELETED through `StorageService.markDeleted` (`summary.sheetDeleted`), and identity's housekeeping at 04:30 removes its bytes. Jobs are never deleted.

## 6. The importers

| Kind | Key | What a row does |
|---|---|---|
| PRODUCTS | SKU | category (full path `Хүнс / Гурил` or a leaf name only one category has; `AMBIGUOUS` otherwise), base unit (default the piece unit), barcodes of the base unit and of the box (several per cell, split on spaces, `,`, `;` or new lines), box quantity → a box unit (a different factor on an existing product is `MISMATCH`: factors change only on the product page), VAT type (code or Mongolian label), weight, home warehouse (WHOLESALE, code or name), fixed shelf (an active STORAGE/PICKING bin of the given or current home warehouse; without one `REQUIRED` on the home column), supplier (code, else name) → main supplier link. Existing products get only the fields that differ; empty cells never clear anything |
| CUSTOMERS | code | kind from the registration number, else the TIN's length, else company with `KIND_GUESSED`; TIN, consumer number, phone, address with the GPS point of a Google Maps link (added when the customer does not have that address yet; the first becomes the default), credit limit and payment term (blank limit = not decided); an inactive customer is reactivated with `REACTIVATED` |
| SUPPLIERS | code, else name | TIN, phone, email, address, bank, payment term; a contact person is added when the supplier does not have them yet |
| RECEIPTS (ADR-0078 #7) | date + supplier + note number | the dialog names a wholesale warehouse the user writes for and the payment (CREDIT, or CASH/BANK with an active account of that kind), sent as `receiptOptions` and stored in `options`; a day `YYYY-MM-DD` not after today (`FORMAT`, `OUT_OF_RANGE`); a supplier by code, else name, active (`NOT_FOUND`, `AMBIGUOUS`, `NOT_ALLOWED`); a product by SKU or barcode (both given must agree, `MISMATCH`; neither ⇒ `REQUIRED`; a box barcode names the box unit), active and allowed in the warehouse by the home rule (`NOT_ALLOWED`); the unit as written, else the barcode's, else the base (`NOT_FOUND`, `INEXACT`); qty > 0; the unit price as printed (2 decimals) only when the creator holds `inventory.costs.manage` (else `PRICE_IGNORED`); ≤ 500 lines per note (`TOO_MANY_LINES`); each note becomes one DRAFT receipt through `ReceiptsService.createInTx` (fixed shelf, else RECEIVING), counted as `summary.applied.receipts` |
| ISSUES (ADR-0081 #7) | date + expense type + recipient | the dialog names a warehouse or store the user writes for, sent as `issueOptions` and stored in `options` (another kind ⇒ `WAREHOUSE_KIND_NOT_ALLOWED`); a day `YYYY-MM-DD` not after today (`FORMAT`, `OUT_OF_RANGE`); an expense type by name, active (`NOT_FOUND`, `NOT_ALLOWED`); the recipient (required) as a customer code, else a supplier code or name, else one active customer of that exact name, else one active staff member of that full name, else a free-text (OTHER) recipient as written (≤ 200); a product by SKU or barcode as for receipts; the unit as written, else the barcode's, else the base (`NOT_FOUND`, `INEXACT`); qty > 0; note ≤ 500; ≤ 500 lines per issue (`TOO_MANY_LINES`); each group becomes one DRAFT issue through `GoodsIssuesService.createInTx` (fixed shelf while it holds the product, else the fullest), counted as `summary.applied.issues`; nothing is posted |
| OPENING_STOCK | warehouse + SKU + bin | one `OPENING` adjustment per warehouse posted at commit (`AdjustmentsService.postSystemInTx`); quantity in the row's unit (default the base unit; must be exact in base units); bin optional: the product's fixed shelf, else SALESFLOOR at the supermarket, else the warehouse's `NOSHELF` storage shelf «Тавиургүй» (sellable, created on demand) with `NO_SHELF`; cost optional (per row unit, ex-VAT): empty = 0 with `NO_COST`; a RECEIVING bin warns `NOT_SELLABLE`; the home rule applies (`NOT_ALLOWED`); a warehouse with an active opening import refuses another (`ALREADY_IMPORTED`); more lines than one posting allows (`MAX_MOVEMENTS_PER_POST`) is `OUT_OF_RANGE` |
| PRICES (ADR-0054) | SKU | name, base unit and packs are for reading only; an empty price keeps the product's terms (UNCHANGED); a filled one needs whole tugriks above 0 (`NOT_WHOLE`, `NOT_POSITIVE`), a live profile by name (`NOT_FOUND`, `ARCHIVED`) with values on the day (`NO_PROFILE_VALUES`), for a product with packs the whole pack by its unit name or code among its packs (`REQUIRED`, `NOT_FOUND`; a product without packs leaves it empty, `NO_PACKS`), a day `YYYY-MM-DD` of today or later (empty = today; `FORMAT`, `PAST_DATE`); an inactive product with a price is `NOT_ALLOWED`; CREATE when the product has no terms that day, UPDATE with the changed fields, UNCHANGED when equal; written by `ProductPricesService.setManyInTx` under `product_prices` locked SHARE ROW EXCLUSIVE; waiting products the commit priced completely from today are completed (`SaleReadinessService.completeManyInTx`), counted as `summary.applied.COMPLETED` |
| LEVELS (ADR-0039) | warehouse + SKU | the low-stock minimum and maximum of a product in a wholesale warehouse or the supermarket (code or name), in the row's unit (default the base unit; exact in base units, 0 allowed); an empty cell keeps the stored level, a row with neither is `REQUIRED`; the resulting minimum above the maximum is `MIN_ABOVE_MAX`; the home rule applies to wholesale warehouses (`NOT_ALLOWED`); CREATE when the product had no levels there, else UPDATE / UNCHANGED; written by `ProductLocationsService.setLevelsManyInTx` |

Row error codes: `REQUIRED`, `FORMAT`, `TOO_LONG`, `DATE_IN_CELL`, `FORMULA_WITHOUT_RESULT`, `ERROR_VALUE`, `NOT_FOUND`, `AMBIGUOUS`, `DUPLICATE_IN_FILE`, `TAKEN`, `NOT_ALLOWED`, `MISMATCH`, `INEXACT`, `NOT_POSITIVE`, `OUT_OF_RANGE`, `ALREADY_IMPORTED`, `MIN_ABOVE_MAX`, `PAST_DATE`, `NOT_WHOLE`, `ARCHIVED`, `NO_PROFILE_VALUES`, `NO_PACKS` (ADR-0054); warnings: `NUMERIC_CODE`, `KIND_GUESSED`, `NO_COST`, `NO_SHELF`, `NOT_SELLABLE`, `REACTIVATED`. Messages: `imports.issues.<code>` in `mn.json`.

## 7. Revert per kind

- products: created products become INACTIVE, wait for their prices again (`sale_ready_at` cleared) and release their barcodes (refused while one holds stock, `IMPORT_REVERT_BLOCKED` with the first SKU); the supplier links the import added are removed and home warehouses and fixed shelves return to what they were; on existing products the updated fields go back only where they still hold the imported value, and the barcodes and box unit the import added are removed / retired if still there;
- customers and suppliers: created ones become INACTIVE; updated fields and credit terms go back only where they still hold the imported value;
- levels: the previous minimum and maximum go back where the imported ones still stand (`restoreLevelsInTx`); a location row the import created and left empty is removed;
- prices (ADR-0054 #6): rows are never deleted, so the revert writes forward under the same table lock (`restoreManyInTx`): an imported row that still holds (its end unchanged and not passed) is closed today, or on its first day when it has not started, and the terms it replaced continue from then up to its end; a product without earlier terms is left without; a row changed since stays. Products the import completed whose terms went back return to «Үнэ хүлээгдэж буй» unless completed again since (`ProductLifecycleService.markWaitingInTx`, audited `UNCOMPLETE`);
- receipts (ADR-0078 #7): the drafts are cancelled (`ReceiptsService.cancelDraftsInTx`) while every one is still an untouched draft; a posted or edited one refuses the revert (`IMPORT_REVERT_BLOCKED`, `reason` POSTED / CHANGED);
- issues (ADR-0081 #7): the drafts are cancelled (`GoodsIssuesService.cancelDraftsInTx`) while every one is still an untouched draft; a posted or edited one refuses the revert (`IMPORT_REVERT_BLOCKED`, `reason` POSTED / CANCELLED / CHANGED, `issueId`).
- opening stock: an `OPENING_REVERSAL` adjustment per document (`AdjustmentsService.reverseOpeningInTx`, `adjustments.reverses_adjustment_id` unique, so never twice); refused when the stock has moved on and the reversal would overdraw (`STOCK_INSUFFICIENT`).

**Lock order (ADR-0044 #5).** A products commit locks the existing products it changes by id (`CatalogImportService.lockManyInTx`) before touching them, then writes `product_locations` (`setManyInTx`), then `product_suppliers` (`linkManyInTx`). A revert does the same: products first (by id), then locations, then links. A registration takes the tables in this order too, so neither ever waits for the other in a circle (`registration-races`).

## 8. Error codes introduced

`IMPORT_STATE_INVALID`, `IMPORT_HAS_ERRORS`, `IMPORT_BUSY`, `IMPORT_REVERT_BLOCKED` (409), `IMPORT_FILE_INVALID` (422). Also used: `VALIDATION_FAILED` (422), `NOT_FOUND` (404), `FORBIDDEN` (403), `STOCK_INSUFFICIENT` (409, revert).

## 9. Audit

`CREATE`, `COMMIT`, `REVERT` on `import_jobs`; the rows each owner service writes inside the commit (products, units, barcodes, product locations, product suppliers, customers, addresses, contacts, suppliers, bins, adjustments) through `AuditService.recordMany` in chunks; a revert's deactivations are `UPDATE` rows with the status and released barcodes before and after.

## 10. Screens (`apps/web`)

Menu «Систем» → «Импорт» (`imports.manage`): `/imports` — a card per kind with the hint, «Загвар татах» and «Файл оруулах» (the «Орлого (падаан)» card first asks for the warehouse, the payment and, for cash or bank, the account; «Файл оруулах» waits for them) (an `.xls` is refused before uploading; the file is sent as `.xlsx` whatever the browser reports), then the history; `/imports/:id` — status, progress while the worker runs (polling every 1.5 s, paused in a hidden tab), counts, file problems, the rows filtered by errors / warnings / all with the first cells in template order plus every cell with a problem and the Mongolian messages, «Системд оруулах» with a confirmation (VALIDATED only), after a price import the number of products it completed, «Буцаах» (a price import explains what goes back) (only the newest committed import, with the reason shown otherwise); an import whose rows the housekeeping deleted shows its counts and «Энэ импортын мөрүүдийг 90 хоногийн дараа цэвэрлэсэн» instead of the rows.
